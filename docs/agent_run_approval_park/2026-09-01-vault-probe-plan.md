# Probe the vault, so a vault-routed deliverable is verified rather than excused

**Status:** executable · **Owner:** Marco Altmann · **Written:** 2026-09-01
**Origin:** open risk 3 of [2026-08-31-approval-park-implementation-plan.md](2026-08-31-approval-park-implementation-plan.md),
which slice 16 mitigated but did not close.

## The defect, restated

Slice 16 gave a vault-shaped artifact reference its own arm in `AgentVerifier`'s probe, so a step that
obeyed the vault hint stopped reading `NOT FOUND`. But that arm is **neutral in both directions**
(`AgentVerifier.cs:553-557`): it returns no size, no mtime and no existence check.

So a step that genuinely delivered to the vault and a step that wrote nothing and merely *claimed* a vault
reference produce **byte-identical prompts**. The trigger is `StepOutcomeClaim.ArtifactRef` — model-authored
free text. That is precisely the lie the probe block exists to catch, and it is reachable in practice: a
parked `create_source` (`BackgroundAssistantTurnRunner.cs:629`) executes no write at all, while the step can
still report the reference it intended.

## The fix

Give the vault its own probe root and turn the existing neutral `VaultReferenceArm` into a real stat on whichever channel names a vault reference — do NOT touch the declared half. Split AgentVerifier.cs:283 so the settings read is unconditional, derive `vaultRoot = AssistantWorkspace.VaultRootFor(settings.AssistantFilesFolder)`, and pass it into the existing time-boxed `Task.Run` alongside `configured` (the `Directory.Exists` on it must stay inside the 2 s box, same dead-UNC reason as the comment at :292-297). In `Probe`, replace the arm with MemoryService's exact chain in MemoryService's exact order: `VaultReference.NormalizePath` → `SafeFolderPath.TryResolveInsideAllowingAbsolute(vaultRoot, normalized, …)` → require the resolved-relative form to start with `VaultTargetPolicy.SourcesPrefix` → `FileInfo`. The asymmetry is the whole change: vault root unconfigured or absent keeps today's neutral arm, but vault root present and file absent is a MISS-flavoured arm counted in its own `vaultMissing` tally — that is what makes a parked, never-executed `create_source` read as missing instead of as "not probed". The declared half keeps its `NOT FOUND` verbatim, because on a vault-routed step that is a TRUE mechanical fact (the file genuinely is not in the working folder) and it already renders on the same line as the vault fact, so the pair reconciles itself: `declared: urlaub-2026.md → NOT FOUND; reported: sources/hr/urlaub-2026.md → found in the vault (5.2 KB, modified 2026-09-01 08:14Z)`. One clause added to the standing guidance at :138 tells the critic how to read that pair, anchored on the vault FIND, never on the step's claim.

**Owner decision, 2026-09-01:** the vault-miss arm ships with **neutral wording**, consistent with the
existing `NOT FOUND` guidance. Teaching the verifier about withheld or unreplayed approval rows so it can
name the park explicitly is a larger, separate change; this design does not foreclose it.

## The test that pins it

`VerifyAsync_VaultRoutedStep_ProbesTheVaultAndKeepsTheWorkingFolderMiss` — one `[Theory]` with the same context twice (declared `urlaub-2026.md`, reported `sources/hr/urlaub-2026.md`, `_settings.AssistantFilesFolder = _dir`), differing only in whether `<_dir>\Vault\sources\hr\urlaub-2026.md` was written. With the file: the step line contains `reported: sources/hr/urlaub-2026.md → found in the vault (` and `ProbeCounts(ProbeLine)["vaultFound"] == 1`. Without it: the same half reads the MISS arm and `vaultMissing == 1`. In BOTH cases assert the declared half still reads `declared: urlaub-2026.md → NOT FOUND` on that same line. That one test pins the positive fact, the parked/lying miss, and the deliberate decision not to rewrite the declared half.

## Why not the cheaper options

The cheapest option — vault-side A, suppress the declared NOT FOUND when the reported ref is vault-shaped, adding no I/O and no dependency — is not merely insufficient, it is worse than doing nothing. Without a stat it instructs the critic to accept an UNVERIFIED MODEL CLAIM as satisfying a declared artifact: the trigger is `StepOutcomeClaim.ArtifactRef`, model-authored free text, and the file-not-produced case and the file-produced case become byte-identical in the prompt. That is precisely the lie the block exists to catch, and it is not hypothetical — a parked `create_source` (BackgroundAssistantTurnRunner.cs:629) executes no write at all while the step can still report the ref it intended. The second-cheapest option — prompt sentence only, no code — has the same defect for the same reason. The stat is the only part of this change that adds information; everything else is bookkeeping around it. Conversely, the two things the investigators wanted that I am NOT building are genuinely unnecessary: a recursive leaf search under `sources/**` (a false-FOUND machine against the user's entire vault history, inside a 2 s box) and any rewrite of the declared half (both facts already land on one line, and the LLM rendering them is the block's stated design).

## Claims checked against the code

- **REFUTED** — VAULT-SIDE rec A (and PROBE-SIDE half B): rewrite the declared half's NOT FOUND into "delivered to the vault as <ref> — not probed" when the same step's reported ref is vault-shaped.
  <br>*Evidence:* AgentVerifier.cs:553-557 already returns the NEUTRAL VaultReferenceArm for any `sources/`-prefixed ref on BOTH channels, with `Resolved` null and size 0. So a step that wrote nothing and reports `artifact_ref: sources/report.md` already gets "not probed" on the reported half; vault-side A would additionally launder its declared TRUE `NOT FOUND` into "not probed". Net result on a lying step: the critic gets zero mechanical evidence where it previously got one true fact. Nothing in either option verifies the claim — the suppression trigger is model text (`StepOutcomeClaim.ArtifactRef`, IAgentTurnExecutor.cs:112, documented as model-authored free text).
- **REFUTED** — VAULT-SIDE: "B is BLOCKED — a positive vault probe needs a recency gate and RunContext has no run-start timestamp (only a per-dispatch Stopwatch at RunContext.cs:37)."
  <br>*Evidence:* An EXACT stat of the reported ref against the vault root needs no recency gate: there is no leaf-matching, so MarkdownExportService's `Vault\sources\Exports` tree (MarkdownExportService.cs:437) cannot collide. The probe's design already handles staleness the right way — it emits `modified <utc>Z` as a fact and lets the LLM weigh it (class comment AgentVerifier.cs:25-27: "it can never itself fail a verdict: the LLM still renders it"). Building a gate would replace an emitted fact with a hidden threshold.
- **REFUTED** — VAULT-SIDE: gate any vault arm on `ctx.WorkspaceRoot is not null`, because that is the only state where the vault sits outside the probe root, and it mirrors `StepHintApplies`.
  <br>*Evidence:* On a non-workspace run `root` = AssistantFilesFolder, so `sources/x.md` resolves to `<folder>\sources\x.md` — NOT `<folder>\Vault\sources\x.md` (AssistantWorkspace.cs:37). The memory tools are vault-relative regardless of workspace (MemoryService.cs:875 normalizes and resolves against VaultRoot unconditionally), so the gated version leaves every non-workspace `create_source` deliverable with no evidence. The "double-probe / self-pair" fear is unfounded: the two resolutions are different paths.
- **CONFIRMED** — BOTH: reaching the vault root from AgentVerifier is layer-legal.
  <br>*Evidence:* tests/Pia.Wpf.Tests/Architecture/LayerDependencyTests.cs has exactly four rules: ViewModels↛Infrastructure, Services↛ViewModels, Models↛Services/ViewModels, Infrastructure↛ViewModels/Services. Services→Infrastructure is unrestricted, and AgentVerifier.cs:8 already has `using Pia.Infrastructure;`.
- **UPHELD, for a stronger reason than the one given.** — PROBE-SIDE: reject option C (inject VaultPathProvider) as "pure test churn for a theoretical race".
  <br>*Evidence:* `VaultPathProvider()`'s parameterless ctor falls back to `%LOCALAPPDATA%\Pia\Vault` (VaultPathProvider.cs, `DefaultRoot()`). Injecting it means 6 construction sites (AgentVerifierTests.cs:73, AgentVerifierWorkspaceRootTests.cs:52, DeclarationClassifierParityTests.cs:96, DeclarationCorpusReplayTests.cs:161, NearDuplicateDeliverableTests.cs:151, AgentRunNudgeParityTests.cs:244) where one lazy `new VaultPathProvider()` silently stats the DEVELOPER'S REAL VAULT during `dotnet test`.   <br>*Evidence:* AgentVerifier.cs:567-569 does a PRE-RESOLVE prefix match. Slice 16 did not just fail to close risk 3 on the declared channel; it opened a fresh hole on the reported one.
