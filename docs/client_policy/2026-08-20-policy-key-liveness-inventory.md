# Policy key liveness inventory

Generated 2026-08-20 as the evidence base for `docs/client_policy/2026-08-20-policy-apply-latency-design.md`.
Every one of the 100 settable `AppSettings` properties, classified by whether a mid-session policy
change reaches its consumer. Verdicts were produced by a per-key grep of every read site and then
adversarially re-checked by a second pass instructed to default to `restart-required`; 22 verdicts were
corrected on review and are marked. `denied` means the key is in `ClientPolicyContract.DeniedKeys`, so a
server policy can never set it (the device `policy.json` still can, for the three device-settable ones).

Verdicts: **live-already** = an existing consumer re-reads per use or on `SettingsChanged`, so the
coordinator's `Get`+`Save` is enough. **live-with-work** = one named piece of wiring is missing.
**restart-required** = read once and latched. **no-runtime-effect** = persisted state with no
enforcement meaning.
