## 1. What this settles, and what it cannot

**Settles:** A2 — *route `ArtifactRef` through the existing artifact probe.* The deferral rested on a

## 2. The pre-registered A2 decision rule

The metric is `artifactReported=True` as a share of **step outcomes** — not of runs. Twelve runs is
roughly 25–35 step outcomes, so the denominator is read off the log, never assumed.

| Reading | Decision |
|---|---|
| **≥ 40%** of step outcomes | **Build A2.** The report channel carries enough to be worth probing. |
| **≤ 12%** of step outcomes | **Drop A2**, and reopen A7's question separately. The channel is empty seven times in eight, which is what the replay reading named as the drop trigger. |
| **12% – 40%** | **A2 stays deferred.** Record the number, and name in §6 what specific observation would move it out of the band. Not "gather more data". |

The middle band is written down on purpose, because it is the likeliest landing place and the earlier
readings (12%, 25%, 29%) all sit in it. A rule with a hole where the answer probably falls is not a
rule.

**A3, A6 and A7 stay closed** until this answers. A3 depends on A2. A6/A7 were never gated on supply.

**Two secondary numbers are recorded but decide nothing here:** the collapsed distinct-artifact
file-shapedness, and whether any declaration still offers alternatives. The first is the gate-A1 metric
and has already answered (56%, gate did not close). The second answered 0-of-6 on the replay; a non-zero
here would reopen **P3**, which was decided-and-not-built on exactly that condition.

## 3. Instrument guards — read these BEFORE reading anything else

All five must be checked, and the first three must read **zero**. A non-zero value in any of them means
the numbers below are instrument error or a censored sample, not a finding.

| Grep | Must be | Why |
|---|---|---|
| `Working subpath did not resolve` | 0 | Otherwise `notFound` is the probe failing, not a miss. |
| `Artifact probe skipped` | 0 | A verify that produced no tally at all. |
| `Artifact probe failed` | 0 | Named in the brief's harvest block; the replay confirmed all three at zero. |
| `overReportCap` | 0 | Non-zero ⇒ declarations past `MaxReportedDeclarations` were never classified, so file-shapedness loses its tail. |
| `overPathCap` | 0 | Non-zero ⇒ candidates past `MaxProbedPaths` were never probed, so delivery loses its tail. |

A 12-run corpus on a six-category mix makes censoring materially likelier than the 4-run pilot did,
which is why the last two are promoted from a footnote to a guard.

Harvest discipline, from the runbook's three traps: attribute on the `[run <id>]` prefix (runs execute
concurrently), take the **last** probe line per run id (`declared` accumulates across verify passes),
then collapse replan twins by hand. Pull the lines into a scratch file every three or four runs — the
file sink rolls at 10 MB over 7 files and a Debug corpus is verbose.

## 5. Protocol, and what else this one session serves

**Provider: Mistral Medium 3.5** (`mistral-medium-latest`), the profile's configured Assistant default
and the replay's provider. Fixed across the whole corpus. If it fails for planning the fallback is the
OpenRouter provider (`openai/gpt-5.6-terra`), and §6 says which one actually ran.

**Build: Debug.** `SensitiveDebug` is `[Conditional("DEBUG")]`, and the per-declaration facts block is

**Profile:** a throwaway root, seeded per the runbook's corrected recipe — `providers.json` **and**

`ScheduledMaxSteps` is deliberately **left alone**. Lowering it to force a budget park would also lower
the *resume* budget — `ResumeAsync` reads the same setting for every run — so the run just re-parks. The
ungroundable park from prompt 4 is a `WaitingForInput` park through the same claim and costs nothing.

**Three other rows ride this session**, because the desktop is the scarce resource and none of them

- **E7(a)** — eyeball the persona and effort pickers in the Routines editor, including the "no longer

- **E7(b)** — one open against a **pre-change** profile, to exercise migration half (b), the `ALTER TABLE`

- **E9** — park prompt 4, **move the per-mode persona in Settings**, then resume. Without the mid-park

  is the persona stamped on each step's persisted message (`SyncMessagePersona`, written unconditionally

## 10. Four collection traps, two of them new

1. **The log truncates tool-call arguments.** 40 of 99 `emit_plan args:` lines end in `…`, so harvesting
   declaration *text* from the log silently loses whatever sits past the cut — including, on this corpus,
   every declaration of two runs whose probe lines showed declarations. **Read `AgentSteps.ExpectedArtifact`
   from the database instead.** It is untruncated and it is what the verifier itself reads. The counters on
   the `Artifact probe:` line stay authoritative for counts; only the strings need the database.
2. **The last probe line can UNDERCOUNT a run.** The runbook's trap 1 says `declared` accumulates across
   verify passes, so take the last line — true, and `18604136` proves it (a first pass read
   `declared=1 notFound=1` before the file existed; the last read `declared=4 found=4`). But a run that
   **fails after its last verify pass** never reports what it declared afterwards: `2dcc6fd2` persisted five
   declarations and its only probe line saw three. That is the whole gap between the two collapse
   denominators in §7. Reconcile the probe line against the step rows before quoting a total.
3. **Count guard *values*, not guard *names*.** Every probe line literally contains `overReportCap=0`, so a
   substring grep for the counter reports one hit per run and looks alarming. Match `=[1-9]`.
4. **`ww_set_value` on the composer works, but reading it back does not prove it.** The first dispatch of
   this session looked like a failure: after `ww_invoke` the composer read empty and *Run in background*
   read disabled, so the prompt was re-sent — and both dispatches had in fact run. The empty composer was
   the **success** signal, because a dispatch clears it. Verify a dispatch by the run row appearing, never
   by the composer's contents afterwards.

Two smaller ones for whoever repeats this: `AgentRuns.CreatedAt` is stored **UTC**, so a
"runs since I started" filter written in local time silently excludes everything; and a run can create
`ScheduledJobs` rows of its own, which then fire.

## 11. Limits

1. **13 runs, one machine, one provider, one afternoon, one operator.** Wider than the pilot's four and
   the replay's eight, and still an existence proof rather than a rate.
2. **Post-P8, so comparable to nothing** — §5. The 78.6% / 94.4% collapse and the 85.7% raw figure are a
   new baseline, not a movement against the replay's 100% or the gate's 56%.
3. **The prompt mix is not neutral for the A2 metric.** Nine of thirteen runs declared at least one file,
   which is a property of §5's six categories, not of what a user does all day. §8 names that as the drop
   risk explicitly.
4. **One prompt ran twice** (§6), so the 12-prompt mix is weighted 2× on `A` #1.
5. **Category D had no vault to read**, by construction — the throwaway profile redirects
   `AssistantFilesFolder` and the vault is a subfolder of it. Its two runs are still in every total: one
   failed, one invented an artifact. Neither is evidence about how these prompts behave with real vault
   content.
6. **The corpus ran against a copy of the real profile's chat and todo history**, so categories C and E had
   genuine content to act on. That is a strength for realism and a weakness for reproducibility — nobody
   else's machine reproduces those runs.

## 12. What else this session settled

### E7 — group E goes green

- **(a) The pickers.** `Routines_Field_Persona` offers *"Use the active persona"* plus all 12 personas —
  not roster-gated, as designed. `Routines_Field_Effort` offers *"Use the persona's setting"* plus all six
  `ReasoningEffort` members with readable labels (*"No reasoning"*, *"Extra high"*). A routine saved with
  **Experienced Coder / Extra high** persisted both pins, and both survived a Disable toggle.
- **The "no longer available" row.** Machine-checked with `ww_assert_value`: with the job's `PersonaId`
  pointed at a GUID no persona has, the picker reads exactly **"No longer available"**, and the effort pin
  beside it still reads **"Extra high"** — the two degrade independently, which is the point of the row.
  The unresolvable pin had to be written into the database directly, because no UI can produce one.
- **(b) The `ALTER TABLE` path.** The throwaway profile was seeded from the real `history.db` with both
  `ScheduledJobs` pin columns **dropped**, so `CREATE TABLE IF NOT EXISTS` was a no-op and only the ALTER
  pass could restore them. It did, on the first open, and the app came up clean — the Assistant view
  rendered, which is what the launch selector waited on. Both pins then round-tripped through the editor
  into columns that exist *only* because the migration added them.

### E9 — the write half is confirmed end-to-end; the read half rests on the unit test

- **13 of 13** user-triggered runs carry a persisted `PersonaId`. Not a sample: every run in the corpus.
- The parked run holds `0000000a-…-0002` **across a full application restart**, while
  `modePersonaDefaults.Assistant` was moved to `…0003` in between. So the value is durable and it no
  longer agrees with the current mode default — which is precisely the state a resume has to read
  correctly.
- `ReasoningEffort` reads NULL on all 13, and that is correct rather than a gap: a user-dispatched run
  carries no job pin, and the mode persona sets no effort, so the resolved effort *is* nothing. It also
  means **this corpus does not exercise the effort half at all**; the routine created for E7(a) is the only
  thing in the session carrying an effort pin, and it was never fired.
- **Not verified here:** the resumed run running *as* the persisted persona. The parked run is a
  clarification park, and its resume affordance was not reachable through automation in this session — the
  chat-history row would not activate by click, double-click, `SelectionItemPattern` or Enter, and the Flow
  rail exposed no `Flow_ActionLink_*` element to invoke. That is an automation gap, not a finding about
  E9. The read-back itself is pinned by
  `HeadlessRunLauncherTests.Resume_RunsThePersonaAndEffortTheLaunchResolved_NotTheCurrentModeDefault`,
  which moves the per-mode default mid-park and was checked non-vacuously by reverting each half of the
  read-back separately. **Worth one cheap follow-up**: a reachable selector on the chat-history row, which
  would also unblock any future UI script that needs to open a specific past chat.
