# Git tool pack — implementation plan (2026-07-15)

## Goal & confirmed scope

Add a **git tool pack** the assistant can call during a turn — the same architecture as the
`files` / `todo` / `memory` built-in plugins. Not UI buttons.

Confirmed decisions (from the user):

- **Form**: assistant tool pack (a `GitToolHandler` exposing discrete `git_*` tools the model invokes).
- **Scope**: local **read + write with confirmation**. Read-only commands run inline; local mutating
  commands each surface a confirmation card. **No network operations** (no `fetch`/`pull`/`push`/`clone`).
- **Gate**: only surfaces when **git is installed locally** — decided **at startup** (`GitLocator`,
  prewarmed together with `VsCodeLauncher`), which also enables/disables the settings toggle.
- **Fresh folders**: **no is-repo requirement** — a non-repo working dir can be turned into a repo via
  `git_init`, so the folder need not already be a git repo.
- **Sandbox is absolute**: git **never** operates on a repo outside `AssistantFilesFolder`, in any case.
- **Hooks**: `git_commit` runs with `--no-verify`.

The repo git operates on is the **active chat's working directory** — the exact root
`FilesToolHandler` already resolves: the configured `AssistantFilesFolder` sandbox narrowed per-turn by
`TaskAmbient.Current?.WorkingSubpath`. No new "which repo?" concept is introduced.

## Design spine: the execution boundary defines everything

The registration wiring is mechanical (it mirrors `files`). The load-bearing part is the
**git-execution layer**, because it is what actually enforces the no-network scope, the injection
safety, the privacy rules, and the containment guarantee. Six constraints, baked in from the start:

### C1 — Discrete allowlisted tools, never a generic `git_run(command)`

Each capability is its own tool with typed, validated arguments. The no-network scope is enforced by
*absence*: there is no tool that runs `push`/`pull`/`fetch`/`clone`, so the model cannot reach the
network no matter what it emits. A single string-command runner would reopen both the network scope
and a shell-injection surface — explicitly rejected.

**Read-only (inline, no confirmation):**

| Tool | git invocation (illustrative) | Notes |
|------|-------------------------------|-------|
| `git_status` | `status --porcelain=v2 --branch` | Machine-parse to a readable summary; also fine to return `status` short form. |
| `git_log` | `log --max-count=N --pretty=…` | `N` capped (default ~20, max ~100). No `-p` by default (that's `git_diff`). |
| `git_diff` | `diff [--staged] [-- <path>]` | Optional `staged` bool + optional path (validated, contained). Output capped (see C6). |
| `git_branch` | `branch --list` / `branch --show-current` | List local branches + current. No branch *creation* here (that's a write). |
| `git_show` | `show --stat <rev>` or `show <rev>:<path>` | `rev` validated against an allowlist pattern; no options passthrough. |

**Local mutating (confirmation card, then execute):**

| Tool | git invocation | Destructive? |
|------|----------------|--------------|
| `git_init` | `init` (in the resolved working dir) | No (creates `.git`). Plain confirm. Enables working in a **fresh, non-repo folder** (see C5). |
| `git_add` | `add -- <paths>` | No (stages only). Plain confirm. |
| `git_commit` | `commit --no-verify -m <message>` | No (creates a commit). Plain confirm. `--no-verify` skips repo-controlled hooks (locked decision). |
| `git_switch` | `switch <branch>` / `switch -c <new>` | **Yes** — switching can shed/overlay uncommitted changes. |
| `git_restore` | `restore [--staged] -- <paths>` | **Yes** — discards working-tree / index changes. |
| `git_stash` | `stash push` / `stash pop` / `stash list` | `list` is read-only; `push`/`pop` mutate. Treat push/pop as **destructive**. |

> **Use `switch`, never the legacy `checkout <branch>`** (critic finding, high). `git checkout <name>`
> is overloaded: if `<name>` also matches a work-tree path (and the branch allowlist below *permits*
> path-like names such as `README.md` or `src/x`), git silently resolves it as a **pathspec** and
> overwrites that file from HEAD — data loss disguised as a branch switch. `git switch` never
> interprets a pathspec, so branch ops use it exclusively. File-content restoration is a separate,
> explicit tool (`git_restore ... -- <paths>`).

Argument validation per tool:

- **Paths** go through `SafeFolderPath.TryResolveInsideAllowingAbsolute` against the resolved repo root
  (same guard the files tools use).
- **`git_show`'s `<rev>:<path>` object spec is NOT a filesystem path** (critic, medium). After the
  containment check, convert the resolved OS path to a **repo-toplevel-relative, forward-slash** path
  before composing `<rev>:<relpath>` — `Path.GetRelativePath(toplevel, resolved).Replace('\\','/')`.
  An absolute/backslash path yields `fatal: invalid object name`. Normalize separators for
  `diff -- <path>` and `add -- <paths>` pathspecs too.
- **Revs/branch names** match a conservative allowlist (`^[A-Za-z0-9._/-]+$`, reject a leading `-` so a
  value can't masquerade as a flag).
- The **commit message** is passed as a single `-m` argument value (never concatenated into a command
  string).

> **Residual exec vector (critic, medium):** allowlisting the *verbs* does not close code execution via
> repo-controlled config/attributes — `diff`/`show` run `textconv`/external diff drivers + `core.fsmonitor`;
> `switch`/`restore` run smudge/clean filters; `commit` runs hooks. A repo *inside* the sandbox can carry
> a hostile `.git/config`/`.git/hooks`. `GIT_TERMINAL_PROMPT=0` does **not** stop these. C2's env hardening
> (below) closes the ones we can; hooks are handled by the `--no-verify` decision in C2.

### C2 — Process hardening (`GitProcessRunner`)

A dedicated internal runner (e.g. `src/Pia.Wpf/Helpers/GitProcessRunner.cs` or a private type inside
the handler) that all tools funnel through. `VsCodeLauncher`'s `ProcessStartInfo` shape is the
starting point but its `ReadToEnd()`-then-`WaitForExit()` sequencing **deadlocks** once output exceeds
the OS pipe buffer — and `git diff`/`git log` routinely exceed it. Requirements:

- **Resolve and pin a real `git.exe`** (critic, medium). Probe once and cache (like `VsCodeLauncher`'s
  `_resolved`/`_executable`), e.g. `where.exe git.exe` / a `git --version` probe, and **refuse a
  `.cmd`/`.bat` target**. `ProcessStartInfo.ArgumentList`'s argv-escaping safety contract holds for a
  real `.exe`; for a `.cmd`/`.bat` shim (scoop/choco wrappers) .NET switches to `cmd.exe` escaping and
  can throw or reopen a quoting-injection surface — exactly what `ArgumentList` was meant to prevent.
- **`ProcessStartInfo.ArgumentList`** (per-argument), `UseShellExecute = false`, `CreateNoWindow = true`,
  `RedirectStandardOutput = true`, `RedirectStandardError = true`. No value ever touches a shell.
- Read **stdout and stderr asynchronously/concurrently** with the wait (e.g. `BeginOutputReadLine` +
  `OutputDataReceived`, or `Task.WhenAll` over `ReadToEndAsync()` for both streams) — never sequential
  blocking reads.
- **Timeout** (e.g. 30 s) driven by a single `CancellationTokenSource(timeout)` over both
  `WaitForExitAsync` and the stream reads. On expiry: `Kill(entireProcessTree: true)` **inside
  try/catch** (it throws `InvalidOperationException` if the process already exited), then **await the
  stdout/stderr read tasks and `WaitForExitAsync`** (with a short secondary bound) before disposing —
  otherwise disposing while `ReadToEndAsync` is pending can throw/leak. Return a clean "git timed out"
  error to the model rather than hanging the turn. (critic, low)
- **Non-interactive + hardened environment** so git can neither block on input nor be steered by
  ambient/repo-controlled config:
  - `GIT_TERMINAL_PROMPT=0`, and empty `GIT_ASKPASS` / `SSH_ASKPASS` (never prompt for credentials —
    also a belt-and-braces network guard),
  - `--no-pager` (or `GIT_PAGER=cat`) so `log`/`diff` don't wait on a pager,
  - `GIT_EDITOR=true` and always `commit -m <message>` so a commit never opens an editor,
  - `GIT_OPTIONAL_LOCKS=0` on read paths (avoid touching the index lock),
  - **Config-exec hardening** (critic, medium): `-c core.fsmonitor=false -c protocol.ext.allow=never
    -c protocol.file.allow=user`, and `--no-textconv` on `diff`/`show`. Decide `git_commit`'s hook policy
    **explicitly**: recommend `--no-verify` (repo hooks are out-of-band code execution) — state the
    trade-off (a project relying on commit hooks won't run them) in the plan.
  - **Scrub inherited `GIT_*` redirection vars** (critic, low — closes an env-redirect sandbox escape):
    clear `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, and set `GIT_CEILING_DIRECTORIES` to the sandbox
    **parent** so upward `.git` discovery cannot cross out of the sandbox. Without this, an inherited
    `GIT_DIR`/`GIT_WORK_TREE` could make `--show-toplevel` (C4) report an in-sandbox path while git
    actually writes objects/refs elsewhere.
- **`WorkingDirectory = resolvedRoot`** (equivalently pass `-C <root>`). Never rely on the process CWD.
- Return `(int ExitCode, string Stdout, string Stderr)`; the handler maps non-zero exit to a readable
  error string for the model (git's stderr is usually already human-readable).

### C3 — Privacy logging (CLAUDE.md gate)

Git output is dense with sensitive content: **diffs = file contents**, `log`/`commit` = **commit
messages + author emails**, remotes/status = **paths and URLs**. Returning this to the *model* is fine
(that's the point). **Logging** it is not:

- Any log line carrying git stdout/stderr, a commit message, a path, or arguments → `SensitiveDebug`
  (erased from release IL), never `LogInformation`.
- Any URL that ever appears (e.g. if `git_status` surfaces a remote, or future diagnostics) →
  `SafeUrl.Format`.
- `LogInformation` may carry only the **tool name** and **exit code** — never args or output.
- Even though scope is local-only, treat remote URLs as possible (a diff can touch `.gitmodules`,
  a `.git/config`) — wrap defensively.

### C4 — Repo containment (the sandbox-escape guard)

Git searches **upward** for `.git`. If the configured sandbox is a subfolder of one of the user's real
repositories, a naive `git commit` would mutate that real repo — a sandbox escape. The guard is a single
`git rev-parse --show-toplevel` call (see C5 — this doubles as the is-repo check):

- Run `git rev-parse --show-toplevel` in the resolved root. **Non-zero exit ⇒ not a repo** (friendly
  message). On success, its stdout **is** the repo toplevel: canonicalize it
  (`SafeFolderPath.Canonicalize`, which resolves reparse points → closes the symlink/junction escape) and
  require it to be **inside the configured `AssistantFilesFolder`** (reuse the files-tools containment
  predicate). Toplevel outside the sandbox ⇒ refuse ("the working directory is inside a git repository
  that lives outside the assistant files folder").
- **TOCTOU re-validation is mandatory (critic, high).** For files, the mutation runs in the *deferred
  `Execute` closure*, and the plugin adapter invokes `pluginCall.Execute()` **directly**
  (`BuiltInPluginHandler.cs:179`), never the handler's `ExecutePendingActionAsync` — so nothing re-runs a
  guard placed only in `HandleToolCallAsync`. The sandbox root is *mutable at runtime*
  (`OnSettingsChanged → UpdateFolder`). Therefore: **capture the resolved root at prepare time** (as
  `PrepareWriteFile` captures taskId/touch) and **re-run the full containment guard inside the git
  `Execute` closure**, immediately before spawning any mutating git process — mirroring how
  `FilesToolHandler.ExecuteWriteAsync`/`PrepareDeleteFile` re-validate. Add a containment test that
  re-points the sandbox between prepare and execute and asserts refusal.
- The env-redirect vector (inherited `GIT_DIR`/`GIT_WORK_TREE`) is closed in C2's env scrub — without it,
  `--show-toplevel` can report an in-sandbox path while git writes elsewhere.
- **Locked (decision 3): we never operate outside the sandbox, in any case.** A discovered repo toplevel
  outside `AssistantFilesFolder` is always refused — there is no external-repo mode and no opt-out. This is
  an absolute invariant, enforced on **every** call (read and write) and re-checked in the deferred write
  closure (TOCTOU above).

### C5 — Availability = installed (startup) + enabled + configured. **No is-repo gate.** (locked)

- **`IsAvailable`** (drives tool registration + system-prompt suppression, exactly like Files):
  `GitLocator.IsAvailable && AssistantGitToolsEnabled && AssistantFilesFolder configured`.
  - `GitLocator.IsAvailable` = git installed, **decided at startup** and cached (see "Startup" below).
- **Deliberately NO is-repo check in availability, and none as a hard blocker (locked by user).** The
  folder may not be a repo yet — the assistant must be able to **`git_init` a fresh folder**. So the tools
  surface whenever git is installed + enabled + a folder is configured.
- **Per-call repo discovery** uses a single `git rev-parse --show-toplevel` spawn (shared with C4's
  containment guard):
  - **Non-zero exit ⇒ the working dir is not (yet) in a repo.** For read/write tools **other than
    `git_init`**, return a friendly, actionable message — *"this folder isn't a git repository yet; call
    `git_init` to create one"* — so the model self-corrects. `git_init` itself proceeds.
  - **Success ⇒ stdout is the repo toplevel** → enforce C4 containment. Toplevel outside the sandbox ⇒
    **refuse, always** (C4 / decision 3).
  - ⚠️ Do **not** use `rev-parse --is-inside-work-tree` gated on `stdout == "false"` (critic, high):
    outside a repo it exits **128** with a `fatal:` on stderr and empty stdout — it only prints literal
    `false` inside a bare repo / `.git` dir (still a repo). Gate on **exit code**, reuse `--show-toplevel`
    stdout for containment — one spawn, no false-vs-fatal ambiguity.
- `git_init` note: it creates `.git` at the **resolved (in-sandbox) working dir**; the new toplevel is that
  dir, so it is contained by construction. Initializing while nested inside an *external* parent repo is
  fine and desirable — it creates a separate, contained repo, and all subsequent ops then resolve to the
  in-sandbox toplevel. Still TOCTOU-revalidate the working dir is inside the sandbox before running init.

### Startup — `GitLocator` probe + prewarm (point 1)

- Add a static **`GitLocator`** helper (`src/Pia.Wpf/Helpers/GitLocator.cs`), the git analogue of
  `VsCodeLauncher`: cached `IsAvailable` + a pinned **`git.exe`** path (probe via `where.exe git.exe` /
  PATH; **refuse `.cmd`/`.bat`** per C2). `GitProcessRunner` launches `GitLocator.Executable`.
- In `App.OnStartup`, add a background prewarm (alongside `EnsureEmbeddingModelAsync`), e.g.
  `_ = Task.Run(() => { _ = GitLocator.IsAvailable; _ = VsCodeLauncher.IsAvailable; VsCodeLauncher.TryGetIcon(); });`
  — decides git-installed once and warms `VsCodeLauncher` (also requested) off the UI thread, since both
  spawn `where.exe` / read the registry. The result is cached, so the settings toggle and the first
  `PiaFileChip` render without first-use latency.
- **Settings toggle gating (point 1):** the "Enable git tools" toggle is **enabled only when
  `GitLocator.IsAvailable`**; when git is absent, the toggle is **disabled (greyed)** and shows the
  **default** value (git-absent already makes the tools unavailable via `IsAvailable`, so the stored bool
  is inert). See the settings-VM/XAML items in the checklist.

### C6 — Edge cases & output caps

- **Unborn HEAD** (repo with no commits): `git log` exits non-zero — map to a clear "no commits yet"
  message rather than surfacing the raw error.
- **Detached HEAD**: `git_branch`/`git_status` should report it as such (don't assume a current branch).
- **Not a repo (fresh folder)**: not an error — per C5, read/write tools return a "call `git_init`" hint;
  `git_init` creates a contained repo. **Bare repo / `.git` dir**: `--show-toplevel` still resolves; the
  containment check applies as normal.
- **`index.lock` contention (critic, low)**: a concurrent git process (an editor's git integration)
  holding `.git/index.lock` makes `add`/`commit`/`restore`/`stash` exit 128 with
  `Unable to create '.../index.lock': File exists`. Map it to a friendly, retryable message ("the
  repository index is locked by another git process; try again") — **never auto-delete `index.lock`**.
  (Note: `GIT_OPTIONAL_LOCKS=0` from C2 helps the read paths only; it does not apply to writers.)
- **Large output**: cap returned text like Files' `MaxFormattedWindowChars` (~100 KB). A giant
  `git diff`/`git log` is truncated with a "…output truncated" marker instead of returning megabytes
  into the context window.
- **Dirty-tree awareness for destructive ops**: the confirmation card summary for
  `switch`/`restore`/`stash pop` should state that uncommitted changes may be lost (via the
  destructive-warning path — see below).

## Confirmation-card / destructive handling

The pending-action → card flow already exists (`FilesToolCall` → `PluginToolCall` →
`ActionCardBuilder.Build`). Git mutating tools return a pending action; read-only tools return inline.

`ActionCardBuilder` changes:

- Add **`ActionCardCategory.Git`** to the `ActionCardCategory` enum (it lives in
  `src/Pia.Wpf/Models/ActionCardInfo.cs`, members currently `Memory, Todo, Reminder, Files` — there is no
  default/fallback member, so the `Build` category switch's `_ =>` arm must be considered) and map
  `"git"` → `Git`.
- `FormatToolTitle`: add a git category key + action keys (`git_init` → "Initialize", `git_commit` →
  "Commit", `git_add` → "Stage", `git_switch` → "Switch", `git_restore` → "Restore", `git_stash` → "Stash").
- **Destructive path must be restructured, not mirrored (critic, medium).** Today `isDelete =
  ToolName.Contains("delete") || ToolName == "forget"` and `warningText` is keyed on **`PluginName`**
  (`ActionCardBuilder.cs:40-50`). `git_switch`/`git_restore`/`git_stash` contain no "delete" substring, so
  a naive additive mirror renders them **non-destructive with no warning**, and a single `"git" => key`
  arm can't express three different warnings. Change to a **`ToolName`-based destructive predicate**
  (`{git_switch, git_restore, git_stash} ∪` the existing delete/forget rule) and resolve `WarningText`
  **per tool name**. `git_add`/`git_commit` are plain (non-destructive) confirms.
- `ResolveStatusText` / `ResolveSuccessTitle`: add git entries (or fall through to the generic
  "processing" — acceptable for a first cut, but add explicit ones for polish).
- The card `Summary`/`Details` render the exact git command about to run (e.g.
  `commit -m "…"`, `switch feature/x`) so the user sees precisely what they're approving. The commit
  message is user-content → the card path already detokenizes; ensure no sensitive logging on this path.

**Auto-approve eligibility (locked — none eligible initially):** `write_file` is deliberately **not** auto-approve
eligible (`IToolPermissionService.IsAutoApproveEligible`). Mirror that — the destructive git tools
(`git_switch`, `git_restore`, `git_stash`) must **not** be auto-approve eligible. The non-destructive
writes (`git_init`, `git_add`, `git_commit`) get plain confirmation cards; recommend **not eligible**
initially (a commit / new repo is a durable artifact the user should see), revisit later. Decide this
explicitly in `IToolPermissionService`, not by accident.

- Surfaced in `AssistantSettingsViewModel` (`[ObservableProperty] GitToolsEnabled`, load next to

- Read by `GitToolHandler` in its ctor + `OnSettingsChanged` (same shape as
  `FilesToolHandler._toolsEnabled`).
- **Git-installed gating (point 1):** add `[ObservableProperty] GitToolsAvailable` to the settings VM,
  set once from `GitLocator.IsAvailable` on load. The toggle's `IsEnabled` binds to `GitToolsAvailable`;

  belt-and-suspenders + a clear UI signal.
- Prewarmed at startup (see the "Startup — `GitLocator`" section) so the toggle's enabled/disabled state
  is correct on first open without blocking the UI thread.

- **Fresh-folder flow (point 1)**: a non-repo working dir ⇒ read/write tools return the "call `git_init`"
  hint; `git_init` (after confirm) creates a contained repo; a follow-up `git_status` then succeeds.
- `GitProcessRunner` tests — large-output (no deadlock) + timeout/kill behavior; refuse a `.cmd`/`.bat`
  target.
- Edge cases: unborn HEAD (`git log` → "no commits"); `index.lock` → friendly retryable message.
- `DiRegistrationTests` and the localization-parity tests must stay green.
- **Test-gating note:** the git command/repo tests need a real `git` on PATH. If CI lacks git, gate
  those with a skippable fact (detect git; skip with a reason) so the suite doesn't hard-fail — but keep
  the availability/containment/card tests git-free via the injectable probe.

## Decisions (locked) & remaining minor choices

**Locked with the user:**

- **No network ops** — enforced by tool absence **plus** C2's env hardening (`GIT_TERMINAL_PROMPT=0`,
  empty askpass, `protocol.*.allow`). Repo-controlled filters/hooks (an out-of-band exec vector) are
  mitigated by `--no-verify` + `--no-textconv` + `protocol` flags (C1/C2).
- **Never operate outside the sandbox, in any case** (decision 3) — a repo toplevel outside
  `AssistantFilesFolder` is always refused; no external-repo mode; re-checked in the deferred write
  closure (C4).
- **No is-repo availability gate; support `git_init` on a fresh folder** (decision 1) — tools surface on
  git-installed + enabled + folder; a non-repo dir routes the model to `git_init` (C5).
- **Startup git probe drives the toggle** (decision 1) — `GitLocator.IsAvailable` decided at startup and
  prewarmed with `VsCodeLauncher`; toggle disabled + default when git is absent.
- **Commit skips hooks** — `git_commit --no-verify` (decision 2).
- **Auto-approve** — all git write tools **not** auto-approve eligible initially.

**Minor implementation choices (no user input needed):**

- **`ResolveEffectiveRoot` reuse**: extract a shared helper vs. replicate the ~12 lines in `GitToolHandler`
  (recommend a small shared helper).
- **`AssistantGitToolsEnabled` default** when git is absent: the toggle shows the default (`true`) but is
  disabled; the value is inert because `IsAvailable` already includes `GitLocator.IsAvailable`.

## Suggested build order

1. `GitLocator` + `GitProcessRunner` + their tests (the hard part; hardening + the pinned-exe probe in

   (incl. TOCTOU) / fresh-folder tests.
