# Security Policy

## Supported versions

Only the latest release receives security fixes. Pia updates itself through Velopack, so a machine
that has been online is normally already on it.

| Version | Supported |
|---------|-----------|
| Latest release | Yes |
| Anything older | No — please update |

## Reporting a vulnerability

Email **entwicklung@neo42.de** with `SECURITY` in the subject. Please do **not** open a public
GitHub issue for a suspected vulnerability.

Helpful to include:

- What the issue is and what an attacker gains from it
- The Pia version (Settings → About) and your Windows version
- Steps to reproduce, or a proof of concept
- Any relevant log excerpt — see the warning below before attaching one

You can expect an acknowledgement within **5 working days** and an assessment with a planned fix
window within **15 working days**. We will keep you updated until the issue is closed, and we are
glad to credit you in the release notes unless you prefer otherwise.

## Scope

**In scope** — the code in this repository: the WPF client, the local data stores, DPAPI-protected
secrets, the end-to-end encryption implementation, the assistant tool permission gate, the MCP
plugin host, and the update path.

**Out of scope** — third-party AI providers and their models, third-party MCP servers you choose to
connect, findings that require an attacker to already have administrative access to the machine or
control of the user's Windows account, and reports generated by a scanner without a demonstrated
impact.

## Before you attach a log

Pia's logs are written to be safe to share: user content is compiled out of release builds, URLs are
reduced to a hashed host code, and paths are tokenised. Please still read through anything you attach.

## Security design

Points most relevant to a review, and where to look:

- **API keys** are encrypted at rest with Windows DPAPI, scoped to the current user
  (`src/Pia.Wpf/Infrastructure/`).
- **Optional end-to-end encryption for sync**: per-record AES-GCM data keys wrapped by a
  device-held user master key, which never reaches the server. A client that cannot decrypt a row
  refuses it rather than falling back to plaintext (`src/Pia.Wpf/Services/E2EE/`).
- **Tool permission gate**: write-capable assistant tools require approval, and the surface decides
  the default — an unattended or voice-mode request without a prior grant is refused, not queued.
  Every decision is persisted with the permission tier that authorised it
  (`src/Pia.Wpf/Models/ToolGateEnums.cs`).
- **File and git tools** are confined to a sandbox root the user configures: every path the model
  supplies is validated against it, and a deferred write pins the root it resolved when the action
  was prepared, so an approval cannot be redirected while it waits. The git tools perform no network
  operations.
- **Releases are Authenticode-signed** from an Azure Key Vault certificate with RFC-3161
  timestamping, applied to the executable, the MSI and the update packages
  (`.github/workflows/build-and-release.yml`).
- **Runtime egress** is inventoried in `docs/external_endpoints/` — every external host the client
  can dial, and why.
